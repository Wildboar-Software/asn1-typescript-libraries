# Set Up New Module

## Background

### Giant Dependency Size

When ASN.1 modules are produced from Wildboar Software's ASN.1 compiler, they
should technically work, but often times, ASN.1 modules have a huge number of
dependencies and transitive dependencies. This can result in the compiler
having to compile tens of modules, and usually, most of this compilation is
unnecessary, because only a few symbols are imported into the module of
interest.

For instance, if you define a new X.509v3 extension in ASN.1, you will have to
import `EXTENSION` from `AuthenticationFramework`, and therefore, the compiled
outputs will contain a completely compiled `AuthenticationFramework` module
too, even if `EXTENSION` was all that was needed. Since many modules depend on
this very influential ASN.1 module, it means that this huge ASN.1 module will
result in tens of thousands of duplicate lines of code appearing in each
dependent module unless we define `AuthenticationFramework` as its own package
and alter the compiled outputs to import (and possibly re-export) from the
`AuthenticationFramework` module.

On top of that, as there are often errors produced from the imperfect compiler,
these errors will have to be fixed over and over again, unless the
depended-upon-by-many module is de-duplicated into its own package.

### Errors

As mentioned above, Wildboar Software's ASN.1 compiler is imperfect. It
generally works well with simple, commonplace ASN.1 (assuming it is
syntactically valid), but it tends to falter with extremely parameterized
ASN.1 in particular.

These errors have to be fixed, sometimes before the module can even compile.

Sometimes the ASN.1 compiler cannot determine the tag number of a type that
appears in a `SET` or `SEQUENCE`, and therefore, cannot determine which
encoded component to decode to that field. You might see comments in the
Typescript output that look like:

```typescript
/* FIXME: <identifier> COULD_NOT_RESOLVE_TYPE_DEF */
```

Or even `string` literals in some cases, that look like:

```typescript
"// FIXME: COULD_NOT_COMPILE_TYPE_DECODER"
```

The only commonality is that they all have `FIXME` in them, and I think all
of them come with a `SCREAMING_SNAKE_CASED` identifier giving you a hint of
what went wrong.

These have to be cleaned up as part of preparing an ASN.1 compilation for
publication.

### Streamlining

The functions generated by the compiler are often not efficient or
unnecessarily complex.

For instance, here is the decoder generated for a type that is simply an
alias for an `INTEGER`.

```typescript
function _decode_OR_Phase (el: _Element): OR_Phase {
    if (!_cached_decoder_for_OR_Phase) { _cached_decoder_for_OR_Phase = $._decodeInteger; }
    return _cached_decoder_for_OR_Phase(el);
}
```

This bizarre compiler output was designed to prevent functions from being
`undefined` if Typescript modules are imported in the wrong order (although I am
not sure if this concern applies anymore after transitioning from CommonJS to
ESM), but in some cases, where a decoder is one exported from `@wildboar/asn1`
or `asn1-ts`, it is already guaranteed to be defined, so this weird fluff is a
waste of code and a loss of performance.

The above can be simplified to:

```typescript
export const _decode_OR_Phase = $._decodeInteger;
```

### Fixing unnesting JSDoc

In ASN.1, it is (unfortunately) valid syntax to define an unnamed types,
values, objects, etc. within other types, values, and objects. For example,
the following is a valid ASN.1 type assignment:

```asn1
FamilyReturn ::= SEQUENCE {
  memberSelect   ENUMERATED {
    contributingEntriesOnly   (1),
    participatingEntriesOnly  (2),
    compoundEntry             (3),
    ...},
  familySelect   SEQUENCE SIZE (1..MAX) OF OBJECT-CLASS.&id OPTIONAL,
  ... }
```

Before compiling anything, the Wildboar ASN.1 compiler refactors the unnamed
`ENUMERATED` type used for `memberSelect` out into its own "virtual" type
assignment, called `FamilyReturn-memberSelect` (the naming convention should
be obvious). This results in a file called `FamilyReturn-memberSelect.ta.mts`
being generated (the `ta` stands for "type assignment," which is necessary
for case insensitive file systems like on Windows, since it is valid ASN.1
to have two assignments with the same name in a module whose identifiers
differ only by case). This file contains a type called
`FamilyReturn_memberSelect` (the hyphen is converted to an underscore to make
it a valid ECMAScript identifier).

This type has its own generated JSDoc, which includes the ASN.1 assignment
in which it is defined enclosed in a codefence with language `asn1`. This
code fence appears after the JSDoc line `### ASN.1 Definition:`.

This technique is called "unnesting" (in the parlance of this compiler), and
while elegant, the produced "virtual assignments" don't really have a proper
JSDoc, because there is no original assignment to point to. While I might
change this in the future to simply enclose the original "non-virtual"
assignment in code fences, at the moment, this JSDoc just contains ugly
fake ASN.1 that looks like this:

```typescript
/**
 * @summary PrioritisedObject_Item
 * @description
 *
 * ### ASN.1 Definition:
 *
 * ```asn1
 * PrioritisedObject-Item ::= SEQUENCE { -- REMOVED_FROM_UNNESTING -- }
 * ```
 *
 */
```

These `-- REMOVED_FROM_UNNESTING --` fake assignments need to be fixed by
filling them in with the correct ASN.1. They usually need to be formatted
within the JSDoc as well.

### Barrel File

Previous versions of these packages expected uses to use deep imports
to access the compiled assignments, such as:

```typescript
import { Certificate } from "@wildboar/x500/src/lib/modules/AuthenticationFramework/Certificate.ta";
```

However, ESM (or at least JSR), requires us to explicitly name all entrypoints
to the module.

This means we need to take all the symbols exposed by each file for each folder
(representing a compiled ASN.1 module), and export them from a central
`index.mts` (barrel) file.

This might seem like an easy-to-automate task until you realize that, within the
scope of several ASN.1 modules that share similar subject matter, there are
often duplicate identifiers. The biggest offenders are `BIT STRING`s with named
bits, `INTEGER`s with named values, and `ENUMERATED` types. Each such type
definition produces "short" and "long" symbols for these named bits, named
values, and variants. For example, the following ASN.1 type:

```asn1
AttributeUsage ::= ENUMERATED {
  userApplications     (0),
  directoryOperation   (1),
  distributedOperation (2),
  dSAOperation         (3),
  ... }
```

Produces Typescript like (but not exactly):

```typescript
export const AttributeUsage_dSAOperation: number = 3;
export const dSAOperation: number = AttributeUsage_dSAOperation;
```

That means if that some other `ENUMERATED` within the same ASN.1 module (or
even within the entire ESM module) also has a variant named `dSAOperation`,
there will be a name conflict. The name conflict can even happen between
a variant and another assigned identifier--for example, some ASN.1 module
could name an information object `dSAOperation`.

These naming conflicts must be fixed, usually by removing the conflicting
short forms from the barrel file.

In some cases, two ASN.1 modules compiled and used in the same ESM module
may have conflicting identifiers, so something has to be done to resolve
the conflict.

### Constraints

Wildboar's ASN.1 compiler parses constraints just fine, but does not use
them in any way to produce compiled outputs. Hence, some types have no
constrains when they should.

Here is an example, starting with the ASN.1:

```asn1
AuthorityKeyIdentifier ::= SEQUENCE {
  keyIdentifier              [0]  KeyIdentifier OPTIONAL,
  authorityCertIssuer        [1]  GeneralNames OPTIONAL,
  authorityCertSerialNumber  [2]  CertificateSerialNumber OPTIONAL,
  ... }
  (WITH COMPONENTS {..., authorityCertIssuer        PRESENT,
                         authorityCertSerialNumber  PRESENT } |
   WITH COMPONENTS {..., authorityCertIssuer        ABSENT,
                         authorityCertSerialNumber  ABSENT } )
```

but when compiled into Typescript, it looks like this:

```typescript
export class AuthorityKeyIdentifier {
    constructor(
        readonly keyIdentifier?: OPTIONAL<KeyIdentifier>,
        readonly authorityCertIssuer?: OPTIONAL<GeneralNames>,
        readonly authorityCertSerialNumber?: OPTIONAL<CertificateSerialNumber>,
        readonly _unrecognizedExtensionsList: _Element[] = []
    ) {}
}
```

As you can see in the constructor, nothing actually enforces
`authorityCertIssuer` and `authorityCertSerialNumber` to be absent or
present together. These constraints being enforced is not always necessary,
but it is desirable in the interest of virtuous intolerance.

## When to Use

This is only to be used when invoked by a human explicitly.

## Assumptions

This skill assumes that the user has already created a project within this
Nx monorepo and has extracted and copied the compiled Typescript output files
into `src/lib/modules/MOD_NAME` within that project, where `MOD_NAME` is
replaced with the ASN.1 module name for each ASN.1 module produced from the
compilation process. This also assumes that the project builds if you run

```bash
npx nx run myproject:build --skipNxCache --outputStyle=static
```

where `myproject` is the name of the project. I think some projects expose
a `typecheck` target, which is like `build`, but only validates the code and
produces no build outputs. This might be faster, and you MAY use it instead of
`build` to validate your code, if it is present.

## Workflow

Do these steps in order:

1. Identify when an ASN.1 module is part of the compiled output only as a
   dependency rather than a module of primary interest: in this case, check if
   this module is already exported as a module of primary interest from some
   other package. If so, delete all files for that ASN.1 module within the
   dependent package except for those directly imported. Continuing on the
   earlier `EXTENSION` example, you would delete every file from the
   `AuthenticationFramework` folder except for `EXTENSION.oca.mts`. Then,
   modify the files that remain to trivially re-export the same symbol from
   the package that you are integrating as a dependency instead. This re-export
   should not have any JSDoc associated with it. For styling purposes, put
   each exported symbol on its own line and use trailing commas after the last
   exported symbol.
2. Attempt to fix any syntax errors that you can. If the fix is not obvious,o
   one easy way to see what to do about a syntax error is to check the workspace
   for similar ASN.1 and see what others have done there. If you are unsure of
   what to do, fix what you can and move on. Report to the user if you left
   broken code to be fixed.
3. Even after you fix any syntax errors, there still may be errors that are not
   syntax-violating. Search for the text `FIXME` in the ASN.1-based Typescript
   and fix those. The vast majority of these are going to be failures to
   identify the tags for a type. Just read the corresponding ASN.1 and try to
   figure it out for yourself. If you really cannot, just leave it.
4. Streamline any functions as described above. You can try to invoke
   `node tools/efficient-alias.mjs` for this (you can replace `node` with some
   other Javascript runtime if you want). It takes the file path as
   `process.argv[2]` and converts the encoder and decoder functions in that
   file to more efficient aliases. Definitely do this for anything that is
   an alias to a universal ASN.1 type, but I am not sure if this can be done
   safely for other types. If this causes problems, just undo these changes
   or skip them.
5. All of the symbols, decoders and encoders for types, named integers, bits,
   and enum variants, "component specs," and anything else produced by the ASN.1
   compilation needs to be exported from `src/index.mts`. If there are name
   collisions between named bits, named integers, or enum variants, only export
   the long symbols for those conflicting symbols: exclude the conflicting
   symbols from the `index.mts` "barrel" file. If the conflict involves two
   symbols that are produced from identical ASN.1 (aside from whitespace or
   comments), you can deduplicate these; hoist the symbol up one folder and
   replace the files that define it with re-exports of the new hoisted file. If
   the conflict involves any other combination of symbols, export both symbols,
   leaving an intentional error behind that causes the build to fail. It may
   involve human judgement to figure out what to do next. If a package exports
   a huge number of ASN.1 symbols, you MAY skip creating the `index.mts` file
   for the whole package and instead create one for each ASN.1 module and
   expose all of these modules as their own separate entrypoints. See
   `packages/x500/package.json` and `packages/x500/jsr.json` for an example of
   this.
6. Find all `-- REMOVED_FROM_UNNESTING --` in the ASN.1-based Typescript and
   replace it with the ASN.1 that belongs there. Apply formatting to the ASN.1
   so that it looks "natural."
7. Identify any types that have associated constraints in the ASN.1 and generate
   code to validate those constraints. If it is a `SET` or `SEQUENCE`, a `class`
   will have been generated, and you MAY add constraint-validation code to the
   constructor. In some cases, it will be more efficient to do the constraint
   validation in the decoder function so that you can fail fast. Handle
   constraint violations by throwing an error. If a constraint is violated,
   throw an appropriate error, preferring one defined in the `@wildboar/asn1`
   package. Throw `ASN1SizeError` if a constraint like
   `SEQUENCE SIZE (1..MAX) OF` is violated. Throw `ASN1CharactersError` if a
   prohibited character is used. Throw `ASN1ConstructionError` if a `SET` or
   `SEQUENCE` has a malformed ordering or prohibited combination of components.
   Throw `ASN1OverflowError` if an `INTEGER` or `REAL` exceeds its range
   constraints. Throw `ASN1Error` for anything else. You MUST NOT add validation
   code to encoders.
8. Add a `LICENSE.txt` file in the project, if it does not exist already.
   Copy an existing license from another package and set the year to the
   current year. I do not want you to attempt to recall the MIT license
   from memory.
9. Add a `jsr.json` file if there isn't one already. It should include the
   `LICENSE.txt`, `README.md`, any source files, and exclude any test files.
   The package name should fall within the `@wildboar/` scope. Version
   should be `1.0.0`. License should be `MIT`.
10. Add a `package.json` file if there isn't one already. Do NOT add a
    `description`. Do NOT add `keywords`. For dependencies, use the same version
    spec of `@wildboar/asn1` that all other packages use. Any dependencies that
    you introduced in step 1 MUST be added here using a version spec that
    requires exact major versions and same or greater minor and patch versions
    as the version of the dependency module defined in this monorepo.
    Export `types`, `module`, and `main`. Version MUST be `1.0.0`. License
    MUST be `MIT`. Type MUST be `module`. All other fields in the `package.json`
    can be taken from a sibling project.
11. Add a `README.md` stub by copying the generic parts from
    `packages/cmp/README.md` and leaving out the parts that are specific to CMP.
    Instead of mentioning the transition to ESM, just say that this module is
    ESM-only; packages produced from this skill will never have been CommonJS
    before. Add an "AI Usage Statement" section clarifying that this package
    was onboarded from the raw compiler outputs using AI, and name the model
    name and date.
12. Try to tighten up the Typescript in `tsconfig.json` for the project.
    Enforce `strictNullChecks` and try to fix any obvious errors. If you
    encounter an error that does not have an obvious resolution, just
    leave `strictNullChecks` off. Add other stricter configs and see if you
    can fix those without enormous code changes.
13. Check for slow types using `deno lint --rules-include=no-slow-types`.
    Generally, these can be fixed by simply adding a return type to a function.
    Sometimes constants need a typing that is easy and obvious to add.
    If you cannot do this, carry on with slow types; it is not worth stopping
    your work to fix this. If you see `prefer-const` lint errors, you may
    change these to `const`. Do NOT fix `no-explicit-any`.
14. If the module has any compiled ASN.1 type assignments, sample a few of them
    an pick the most complicated one you find. Add a unit test file called
    `roundtrip.test.mts` in `src/`. This unit test file is intended to check
    that a value of this type can be encoded and decoded back to the same
    original value. In this file, write a test in a suite that constructs a
    valid value of this type (you can look at other compiled code that uses this
    type as an example of how to do this), and encode it using the generated
    `_encode_X` and decode it using the generated `_decode_X`. Compare the
    decoded value to the original value to ensure that they are the same. Wire
    up `vitest` with Nx for the project so that it runs this test file when you
    run `npx nx run mypackage:test` or `npx nx test mypackage` (where `mypackage`
    is the project name). Ensure that the tests to not produce new files in the
    source tree, and fix it if they do. Any generated files belong in `dist`,
    `tmp`, or similar "output" directories. See what other projects do for
    reference.
15. If you are working on the `master` branch, you may run
    `npx cloc@2.6.0-cloc packages/` to count the lines of code and update the
    readme with only the Typescript statistics. Do NOT do this if you are on any
    other branch, because it might introduce merge conflicts that make the
    statistics wrong.
16. In `.github/workflows/publish.yml`, add the new Nx project name to the
    matrix for the `publish` job.

## Output to the User

Report to the user:

1. What package-level dependencies were identified.
2. What ASN.1 modules are now imported from other packages.
3. Whether there were any syntax errors that you could not fix. This is
   important, because it means the module is not going to build.
4. Whether there were any `FIXME` compiler-generated errors that you could not
   fix. 
5. Whether there were any conflicting exported symbols that require manual
   intervention to resolve.
6. What Typescript strictness you were able to add to `tsconfig.json`, and
   notably, whether you were able to enforce `strictNullChecks`.
7. Remind the user to add a description and keywords to `package.json`, and to
   fill in `README.md`.

Include these details in any PR you submit.
